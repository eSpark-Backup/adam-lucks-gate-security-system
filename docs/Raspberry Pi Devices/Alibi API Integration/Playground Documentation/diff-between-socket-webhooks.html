Webhooks vs Socket.IO

Introduction

Both Socket.IO and webhooks are used for real time updates between ACC servers and clients. Webhooks are recommended as they can provide notifications for the whole site, whereas Socket.IO only provides notifications from the server that WEP is co-located with so that the Web Endpoint service, and the Socket.IO connection needs to be run on each server within the site.

Webhooks (Site-wide notifications - Recommended)

Webhooks are callbacks that are triggered by events on the ACC Server. The client can configure a public URL to receive events from an ACC site. Webhooks are available over HTTP/HTTPS protocols and are configured for site-wide communication. Optional heart beat notifications can be configured to make sure connection to the ACC Web Endpoint has not been interrupted.

Pros

  1. ACC Web Endpoint forwards notifications via a non-persistent HTTP/HTTPS connection.
  2. Performs well across a multi-server site.
  3. Server and site-wide notifications are sent to the client.

Cons

  1. Only events are available via Webhooks. To receive ALARM_OBJECTS, CAMERA_OBJECTS, SERVER_OBJECTS and SITE notifications, you will need to subscribe via Socket.IO.
  2. Clients need to setup a receiving HTTP/HTTPS server to make use of this functionality.
  3. Each push to HTTP/HTTPS server initiates a new TCP connection.
  4. Webhooks can only facilitate one-way communication from server to client.

Socket.IO (Server-wide notifications - Not Recommended)

Socket notifications rely on persistent web socket connections between the 3rd party client and ACC Web Endpoint, and a notification channel between ACC Web Endpoint and ACC server. The socket-based connection is configured between a specific server and a client.

Pros

  1. Fast two-way channel between a web browser and a server.
  2. Low latency communication between a client and web service.
  3. ALARM_OBJECTS, CAMERA_OBJECTS, SERVER_OBJECTS, SITE notifications, and events are available through socket connection.

Cons

  1. Session required for full life cycle: A session is required to open the notification channel as well as to keep the notification channel alive. These sessions can expire, which means that the client would have additional work to regenerate a new token and resubscribe to notifications again.
  2. The client has additional responsibility to listen for notification channel disconnect event and re-establish the notification channel subscription if the connection went down for some reason.
  3. ACC Web Endpoint need to be installed on each server and socket.io connection is required for each server to receive site-wide events
  4. Only server-specific notifications are sent to the client.
  5. Performance and Scale : Due to multiple channels for each server, with multiple clients, we have exponential channels open between ACC server and ACC Web Endpoint.

Comparison between Webhooks and Socket.IO

Index Socket.IO Webhooks
Connection Persistent Non-Persistent
Protocol WebSocket HTTP / HTTPS
Ease of Use Clients need to have Socket.IO client Clients need to setup a receiving HTTP/HTTPS server
Session Session-based Session only needed during configuration
